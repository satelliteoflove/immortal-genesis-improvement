2026-11-18 17:15

Object graphics are about ten times cheaper

The game was unpacking object tiles bit by bit every time it drew them, which took over half of all CPU time on level 6. The patch now unpacks them ahead of time into a larger, 2 MB ROM, built from your own copy of the game. Late updates fell from 58% to 20% on level 6 and from 41% to 24% on level 5, and the worst stall on those levels went from 11 frames to 7. Across all levels it's 23.8% down to 16.4%. The other levels barely moved, so something else is holding them back. This also turned up a bug in the original game: a slip in its tile search takes the top off the wall torch's flame. The flame is whole again. All of this is tested in emulators only, and not on real hardware.

2026-11-18 16:49

The BlastEm fork is now the reference

The fork is built from source with two bugs fixed: it wouldn't compile without OpenGL, and headless runs counted every frame twice. Both are logged in docs/blastem-fork-fixes.md to offer back later, and nothing has been submitted. The newer upstream DMA fixes weren't needed. The game's DMA only reads work RAM and ROM around 020000 to 03FFFF, never the range those fixes cover. Runs repeat exactly, and turning the profiler on doesn't change video memory on any level. On this build 23.8% of updates ran late, and 58% on level 6. Object graphics cost a little more than PicoDrive counted, so that routine remains the first target.

2026-11-18 16:17

BlastEm agrees with PicoDrive

The same scripted runs now work on BlastEm, a much more exacting emulator. Across all eight levels 23.0% of the game's updates ran late on both, and level by level the figures match within a point, apart from level 2, where the random walks end early at deaths and prompts. The 4-frame gaps PicoDrive showed don't appear on BlastEm, so they look like a PicoDrive quirk. PicoDrive stays in use for profiling, and BlastEm becomes the check on whether an optimization really helps. None of this has been run on a real Genesis yet.

2026-11-18 15:58

The game runs under test, and the first findings

The game now runs headless with scripted input, and a profiling build of PicoDrive shows where its time goes. All eight levels can be reached directly. The game updates once every 5 video frames, 12 times a second. In random walks 23% of those updates came late, and about half on level 6. On levels 5 and 6 the late ones spend much longer building object graphics. On levels 2, 4 and 8 the cause is still unknown. These timings are from the emulator. Three lives per level is confirmed. After the third death the game offers a new game from the very first room, or asks for a certificate, even though it already has a way to reload a level without one. Details are in docs/how-the-game-works.md. The picture shows the eight levels and stays on this machine.

2026-11-18 15:47

The project starts

This began as an idea for a 32X port. The complaints people have about the game are mostly about its design (deaths with little warning, restarting floors, fights that play alike), and the 32X wouldn't fix those, so it's now a straight patch for the Genesis version. The three goals are fairness, bug fixes, and smoother performance where that's possible. The target is The Immortal (USA, Europe), 1 MB, serial T-50186. Its checksum is correct and its header declares no save RAM. Nothing in the game has been examined or changed yet. The game's screenshots and clips will appear here but stay out of git, so they only show on the machine that made them.
